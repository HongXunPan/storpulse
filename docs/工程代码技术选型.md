# StorPulse 工程代码技术选型

## 1. 当前技术栈

- 共享领域与引擎：Rust 1.97.1 stable，使用 Rust 2024 edition。
- macOS 采集与界面：Swift 6.3、SwiftUI、AppKit、libproc、IOKit。
- macOS 持久化：系统 SQLite3；历史关闭时不创建数据库。
- Windows：阶段 0 使用 Rust 原生 CLI 与 Win32/ETW；Windows x64 开发者预览采用用户主动启用的手动 LocalSystem 服务。持续协议、共享产品 IPC、Win32 ETW 会话、单客户端产品服务循环、独立 SCM 服务、标准用户实机测试客户端、安装卸载和阶段化诊断包已建立；WinUI 3 阶段 2A–2B 内存列表、单实例、通知区域与窗口生命周期已通过 Win10 实机门禁。阶段 2C 使用 Rust 客户端 DLL 独占 SCM、IPC 与协议会话，C#/WinUI 后台任务把批量原始快照交给 `storpulse_ffi.dll` 聚合，失败时显式显示受限或错误，不回退确定性数据。
- Windows 服务契约：`storpulse-windows-service-contract` 是不调用 Win32 的纯 Rust 库，统一普通用户适配层与 LocalSystem 服务的消息、分帧、版本和状态转换；真实管道、ETW 与服务生命周期留在平台运行时。
- Windows 产品 IPC：`storpulse-windows-ipc` 只封装 `StorPulse.Collector.v1` 本地字节流、显式 ACL、分段读写与超时，供标准用户客户端和服务运行时共同使用；不承载 SCM、ETW、状态机或诊断持久化。
- Windows 服务运行时：`storpulse-windows-service-runtime` 接收归一化的进程、线程、磁盘与丢失事件，按会话累计并生成每秒 `RawSnapshot`；同仓 Win32 层负责 LocalSystem/客户端身份、ETW 控制与消费和单会话协议循环，不把平台状态下沉到共享内核。
- Windows 诊断：`storpulse-windows-diagnostics` 复用服务契约中的稳定阶段和安全错误码，负责类型化事件、32 条服务内存环、64 KiB 单条且最多 16 条的原子后备记录；正常采样不写日志，也不新增第三方依赖。
- SQLite 接入：SwiftPM 内的轻量 C target 只暴露系统 `<sqlite3.h>` 并链接 `libsqlite3`，不依赖 Homebrew 或 `pkg-config`。
- 跨语言边界：稳定 C ABI，传递带版本号的批量 JSON 和显式释放缓冲区；Windows 的平台客户端 DLL 与共享引擎 DLL 分别承载平台会话和跨平台聚合，不让 C# 复制产品管道协议。
- macOS 进程边界：C 桥通过 `dlopen` 装载 Rust 动态库，Swift actor 独占引擎句柄；测试产物不进入版本库。
- 当前宿主：macOS 26.5、Intel x86_64；部署目标暂定 macOS 14。

## 2. 依赖准入

Rust 仅允许以下第三方运行依赖：

| 依赖 | 用途 | 许可证 | 平台与体积影响 | 不采用的替代方案 |
| --- | --- | --- | --- | --- |
| `serde` | 稳定领域模型序列化 | MIT / Apache-2.0 | 纯 Rust、三平台可用；只进入共享内核 | 手写解析易产生契约分叉 |
| `serde_json` | FFI 批量快照与隐私导出 | MIT / Apache-2.0 | 纯 Rust；每秒一次批量分配需阶段 0 测量 | 逐字段 C ABI 复杂且演进成本高 |
| `windows-sys` | Windows 探针、产品客户端、IPC 与服务运行时的 Win32、SCM、ETW、TDH 和命名管道绑定 | MIT / Apache-2.0 | 仅 Windows 目标编译；零额外运行时，按 crate 裁剪 feature | 手写 FFI 容易在结构布局、句柄和错误码上出错；高层封装会引入更宽依赖 |

Windows C# 壳层固定使用 .NET SDK `10.0.302`，只准入以下微软官方包：

| 依赖 | 用途 | 许可证 | 平台与体积影响 | 不采用的替代方案 |
| --- | --- | --- | --- | --- |
| [`Microsoft.WindowsAppSDK` `2.3.1`](https://www.nuget.org/packages/Microsoft.WindowsAppSDK/2.3.1) | WinUI 3、窗口与后续 AppLifecycle | Microsoft Windows App SDK 许可 | 仅 Windows；自包含测试包体积明显增加，但目标机无需预装运行时 | WPF 仅保留为 WinUI 回退，不并行维护两套正式界面 |
| [`Microsoft.Windows.SDK.BuildTools` `10.0.28000.2526`](https://www.nuget.org/packages/Microsoft.Windows.SDK.BuildTools/10.0.28000.2526) | 在 CI 固定 Windows SDK 构建工具 | Microsoft Windows SDK 许可 | 仅构建期约 21 MiB，不进入产品业务依赖 | 依赖 runner 预装版本会使 XAML 构建随镜像漂移 |

Swift 不引入第三方包，只使用系统框架。若批量 JSON 的 CPU 或分配开销超过阶段 0 可接受范围，停止继续 UI，实现定长 C 结构批量传输后再评估。

## 3. 默认执行规则

1. 平台 API 只存在于 `platform/macos` 或 `platform/windows`，不得进入 Rust 共享领域。
2. Rust 内核不得保存完整路径、命令行、用户名或文件内容。
3. 计数器下降必须解释为身份变化、重置或数据源变化，不产生负速率。
4. 共享快照只携带来源、范围、新鲜度和完整性，不把 macOS 结论写成 Windows 已支持。
5. 历史和提醒默认关闭；实时样本只保存在内存。
6. Windows 普通日志只记录生命周期、警告和错误并限量轮转；诊断 ZIP 由用户主动导出，不自动上传。

## 4. 最小校验点

- `bash scripts/validate.sh`：格式、Rust check/test/clippy、Swift test、文件预算和差异格式。
- `bash scripts/validate_stage0_macos.sh`：当前宿主 API、真实负载、受限比例和自身开销。
- `./scripts/validate_stage0_windows.ps1`：Windows x64 格式、check/test/clippy、探针执行与隐私字段检查。
- Windows 持续采集实现必须补充 `RawSnapshot v2`、协议状态机、日志轮转、脱敏导出和 Win10/Win11 分离状态的定向测试。
- `cargo test -p storpulse-windows-service-contract`：验证长度分帧、消息版本、状态转换、快照序列和单调时间，不替代 Windows 服务与 ETW 实机测试。
- `cargo test -p storpulse-windows-service-runtime`：验证经典线程/磁盘事件解码、设备与进程累计、PID 复用、短命进程保留、丢失状态和未知辅助指标；服务端命令顺序由 `storpulse-windows-service-contract` 的独立测试覆盖。Windows 目标交叉检查只证明 ETW、身份和服务循环可编译，不替代实机连续传输和清理门禁。
- `cargo test -p storpulse-windows-diagnostics`：验证安全字段、内存环淘汰、同毫秒唯一文件、写前轮转、超限与目录失败，以及正常内存事件不创建诊断目录。
- `.github/workflows/windows-preview.yml`：在 Windows runner 上执行 Windows 工作区测试与产品七包 Clippy，保留阶段 1 服务协议测试包，并把服务、Rust 客户端 DLL、共享引擎 DLL 和 WinUI 3 自包含发布组装为单一阶段 2C artifact；CI 宿主结果不标记为 Win10 或 Win11 实机门禁。
- 当前源码仓是 Swift Package；本机 `xcodebuild -list` 不识别裸包目录，因此现阶段以 `swift test` 为 Swift 门禁，建立正式 Xcode 工程后再补 `xcodebuild test`。
- 任一校验失败、平台指标无法解释或自身出现主动周期性落盘时必须停止。

## 5. 暂不验证

- Windows 桌面日志轮转、后备记录只读导入、阶段 2C 真实采集界面、观察会话、Windows 11 实机和长期自身 I/O；GitHub runner 构建不计入桌面实机门禁。
- Apple Silicon 与 macOS 14–25 实机。
- App Sandbox、签名、公证、安装、更新和卸载。
- 正式构建、归档、打包和发布。
